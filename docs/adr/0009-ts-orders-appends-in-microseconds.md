# A span's `ts` orders appends, so it carries microseconds

ADR-0002 says the latest appended span wins on overlap, and `read_events` resolves that by sorting the ledger on `ts`. With second resolution the stamps of two spans appended in the same second tie, the sort falls through to read order, and read order is month-file order. Filing is by a span's start, so a span that crosses a month boundary is filed under the earlier month: `fix 2026-08-31T23:00 2026-09-01T04:00` lands in `2026-08.jsonl` and loses to a September span it was written to override. Two `fix` commands typed by hand tie easily, and `import-timew` writes every span it imports inside one second. `ts` now carries microseconds and totally orders appends across files. `start` and `end` keep second resolution: a span boundary is entered by hand, and six zeros on it say nothing.

Rejected: defining the winner as the last span in file order, which makes "latest appended" literal and needs no clock, but answers the month-crossing case backwards — the only case where the two orders can disagree. Rejected: microseconds everywhere, which puts `.000000` on every hand-typed boundary to fix a field the user never types. Rejected: a sequence number on each span, exact by construction and independent of clock resolution, but every append would first have to read the highest existing value, and an append that consults what is already there is the one thing ADR-0002 buys by being append-only.

Consequences: events already on disk keep their second-resolution stamps, so two of them appended in the same second across two month files still resolve by file order. That was already true and no rewrite can fix it, because the append order was never recorded. `datetime.fromisoformat` reads both spellings, so there is nothing to migrate. The test suite builds spans through `stamped`, the same constructor the `fix` and `import-timew` paths use, so a seeded overlap resolves the way a real one does.
